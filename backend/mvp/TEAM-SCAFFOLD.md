# SyndaMorph AI Production Team — MVP scaffold (phases 5–8)

This is a **backend contract and deterministic-test foundation**. It does not activate
AI inference, replace the existing converter, change the WordPress UI, or publish
patterns/pages. The current Production simulation remains a simulation.

## Phases / ownership

| Phase | Responsibility | Contract / future adapter |
| --- | --- | --- |
| 5 | PM/Boss classifies job, gives title, complexity, ordered assignments, acceptance criteria | `agents.pm.plan(job)` → `assertPmPlan` |
| 6 | Designer proposes editable layout; Developer prepares implementation proposal | `agents.designer.design(...)` → `assertDesign`; `agents.developer.implement(...)` → `assertImplementation` |
| 7 | Coordinator passes validated outputs and records structured role events | `runTeamPipeline` |
| 8 | Trusted block compiler + independent validator + bounded repair loop | existing `runFidelityLoop`, `compile`, `validate`, optional `repair` |

### Runtime contract

```js
const { runTeamPipeline } = require('./mvp/team-pipeline');
const result = await runTeamPipeline({
  job: {
    brief: 'Convert this section to editable Gutenberg blocks',
    source: { kind: 'html', sectionId: 'hero', label: 'Hero' },
  },
  agents: { pm: pmAdapter, designer: designerAdapter, developer: developerAdapter },
  compile: trustedCompiler,
  validate: independentValidator,
  repair: repairAdapter, // optional; no retries by default
  maxRepairs: 0,
});
```

- All agent adapters **must be injected**. No default simulated outputs are generated by this module.
- PM output is limited to `schemaVersion`, source `sectionId`, `jobTitle`,
  `complexity`, ordered Designer/Developer assignments, and acceptance criteria.
- Designer returns a checked `layoutPlan` plus rationale. Developer returns
  a checked `layoutPlan`, implementation notes, and descriptive custom block
  requests (not executable scripts or HTML).
- Design and implementation cannot switch the selected section identity.
- The existing `plan.js` and `loop.js` enforce bounded structure and
  `passed` + zero failures. The reviewer is an independent injected adapter,
  **not the same AI agent marking its own work correct**.
- A failed validation yields `needs-review`, never automatic approval.
- `published` is always `false`: saving to WordPress is a separate explicit
  action and **is not wired here**.
- Events are stage facts (`classified`, `handoff`, `passed` /
  `needs-review`), not fabricated chat dialogue.
- No model/provider selection policy is baked in yet. Injected provider adapters
  can later use the selected model and token accounting. Benchmark-driven routing
  and temporary freelancer agents remain **future scope**, not implemented.

## Where this stops (intentional)

There is **no** new REST endpoint, model call, provider key requirement, database
schema, dashboard mode, code execution sandbox, WordPress save handler, or
autonomous job scheduler. Do not put this test pipeline behind an apparently
working AI button before a provider and real compiler/validator are connected
and independently validated.

## Run checks

```sh
npm test --prefix backend
node --check backend/mvp/team-contract.js
node --check backend/mvp/team-pipeline.js
```

The test fixture exercises real contract validation using injected deterministic
adapters. Passing tests do **not** prove actual AI reasoning or Gutenberg fidelity.
